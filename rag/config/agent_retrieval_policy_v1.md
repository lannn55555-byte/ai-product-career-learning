# Agent RAG 调用规则 V1

## 调用本地 `retrieve_evidence` 的问题

- AI 概念解释、模型选型、RAG、Tool Calling、Agent、Evals；
- AI 产品学习路线、职业方向、项目/作品集设计；
- AI 功能问题诊断、案例拆解、面试练习与回答复盘；
- 需要引用本知识库中已有框架或案例的请求。

调用时由 Agent 传入当前任务相关的 `stages`。阶段不明确时可先用全库检索，
但回答前应选择最相关的证据，而不是把所有结果直接拼进上下文。

## 不必调用的情况

- 闲聊、纯格式整理，或与 AI 产品目标无关的用户文本改写；
- 例外：当用户要求将简历、项目经历或自我介绍转写为 AI 产品求职材料时，需要调用本地 RAG，
  以核对目标方向、能力框架和表达边界；仍不得把资料库的一般性表述伪造成用户经历。
- 用户明确要求只基于其提供的材料回答。

## 必须同时做当前网络核验的情况

当问题涉及最新/目前的模型能力、价格、招聘、公司动态、法规、产品发布或具体
市场信息时：先调用本地 RAG 取得背景框架，再调用网络工具核验动态事实，优先
使用官方来源。不得把知识库里的旧资料当作实时事实。

## 回答边界

- 把 `evidence` 中的来源链接附在相关结论后；
- 不把链接跳转或导航文字当作该切片本身的事实证据；
- 证据不足时说明不确定性，并建议下一步检索或核验。

## 运行时检索决策

本规则服务于完整的职业学习 Agent，而不只是职业诊断。每一轮先判断当前任务是否需要外部资料，再决定使用哪个资料阶段；阶段不明确时可将全库检索作为兜底。

产品工作流先给出 `current_stage`，它是确定性的上下文，不由模型临时猜测。模型只可在允许的阶段范围内判断是否需要检索、是否需要扩大范围，以及是否必须补充网络核验。

### 四种决策结果

| 决策 | 适用情况 | Agent 动作 |
|---|---|---|
| `no_retrieval` | 只处理用户已提供的事实、纯格式整理、与 AI 产品目标无关的改写或情绪回应 | 不调用本地 RAG，也不附加外部事实。 |
| `local_retrieval` | 需要知识库中的概念、框架、案例、学习路径或面试方法 | 以当前任务允许的 `stages` 调用 `retrieve_evidence`。 |
| `local_plus_web` | 涉及当前模型能力、价格、职位、公司动态、法规、产品发布或其他时效性事实 | 先调用本地 RAG 获取背景，再使用网络工具核验最新事实，优先官方来源。 |
| `ask_for_material` | 结论必须依赖用户未提供的简历、项目材料、JD 或约束条件 | 说明缺少什么材料；不得用通用资料代替用户事实。 |

### 判断顺序

1. 这轮要判断的是用户自身事实，还是外部知识？用户经历、贡献和项目结果只能以用户材料为依据。
2. 外部知识是否为完成当前任务所必需？若只是改写或整理，不检索。
3. 所需外部知识是否会随时间变化？会变化时使用 `local_plus_web`，不得把本地旧资料当作实时事实。
4. 当前工作流允许查哪些资料阶段？仅传入最小必要的 `stages`，需要跨阶段时可传入多个阶段。
5. 取回证据后，只把与当前结论有关的 3–5 段摘要送入模型；不得把全部命中内容拼入上下文。

## 阶段与资料范围

| 当前用户任务 | 默认 `stages` | 何时扩大范围 |
|---|---|---|
| 个人经历提取、简历改写 | 无 | 缺少材料时要求用户补充，不以 RAG 推断经历。 |
| 职业方向与能力证据诊断 | `diagnosis` | 同时输出学习建议时增加 `learning`。 |
| 14/30/60 天学习计划 | `diagnosis,learning,application` | 需要特定面试目标时增加 `interview`。 |
| 每日概念学习与术语解释 | `learning` | 需要产品设计或场景取舍时增加 `application`。 |
| 产品方案、故障诊断、场景题 | `application,learning` | 形成作品集案例时增加 `case`。 |
| 项目案例与作品集包装 | `case,application` | 需要对齐面试表达时增加 `interview`。 |
| 面试准备与回答复盘 | `interview,diagnosis` | 讨论具体项目证据时增加 `case`。 |
| 资源推荐与持续学习 | `resources` | 资源是否最新时额外进行网络核验。 |

## 检索决策合同

编排器在调用检索器前记录下列可审计决策；这不是向用户暴露的隐藏推理，而是产品日志和测试所需的简短理由。

```json
{
  "current_stage": "diagnosis",
  "user_intent": "career_direction",
  "decision": "local_retrieval",
  "rag_stages": ["diagnosis", "learning"],
  "requires_web_verification": false,
  "reason": "需要 AI 产品能力框架说明经历迁移，但不涉及实时岗位信息。"
}
```

字段约束：

- `current_stage` 只能是 `diagnosis`、`learning`、`application`、`case`、`interview` 或 `resources`。
- `rag_stages` 只可包含上述阶段，且在 `no_retrieval` 与 `ask_for_material` 时必须为空数组。
- `requires_web_verification` 只可在 `local_plus_web` 时为 `true`。
- `reason` 只记录可复核的任务理由，不记录模型的隐藏推理。

## 证据使用与失败处理

- 职业诊断必须分开呈现“用户材料中的事实”“本地资料中的框架”和“Agent 基于两者形成的建议”。
- 模型不得把检索片段中的一般性表述写成用户已经具备的经历或能力。
- 所有由本地资料支撑的外部事实，附上对应的标题和来源链接；没有足够证据时，明确标记为不确定。
- 检索器无命中、返回低相关结果或资料不覆盖当前问题时，Agent 应说明知识库不足，选择 `ask_for_material`、网络核验或保守回答；不得编造引用。
- 对同一用户请求，编排器最多发起一次本地检索；只有用户补充了关键材料、切换了任务阶段，或明确请求继续深挖时才重新检索。

## 最小测试集

在接入诊断 Agent 前，至少验证以下决策：

1. “我做过三年用户研究” → `no_retrieval`。
2. “我的用户研究经历如何迁移到 AI 产品？” → `local_retrieval`，`diagnosis`。
3. “我只有 14 天，应该如何学习？” → `local_retrieval`，`diagnosis,learning,application`。
4. “RAG 和 Tool Calling 有什么区别？” → `local_retrieval`，`learning`。
5. “某公司现在的 AI 产品岗位要求是什么？” → `local_plus_web`，先本地检索再网络核验。
6. “把这段项目经历改成 STAR” → `no_retrieval`。
7. “请判断我是否适合转行，但我不提供任何经历。” → `ask_for_material`。
